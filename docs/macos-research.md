# Native macOS Port: Technical Research

Research checked against Apple primary sources on 2026-09-30. **API facts** below describe documented behavior; **recommendations** are proposed project choices requiring implementation evidence. This file supports the migration plan, rather than claiming that a native prototype has been tested.

## Recommended architecture

Use Swift with an AppKit document shell: `MDWriteDocument: NSDocument`, `NSDocumentController`, one `NSWindowController` per document, and an `NSTextView` in an `NSScrollView`. Apple provides the document/controller/window architecture and text view editing machinery. Optional SwiftUI preferences or accessory views can follow after the core works. Keep one owner for document state and undo; avoid a competing SwiftUI document lifecycle. [NSDocument](https://developer.apple.com/documentation/appkit/nsdocument/), [TextKit](https://developer.apple.com/documentation/appkit/textkit)

Port editor mutations and Markdown span detection into a UI-independent Swift module. Existing behavior is defined by `src/EditorMutations.js`, `src/markdownhighlighter.cpp`, and `tests/tst_mdwrite.cpp`; those provide parity fixtures, not a reason to embed Qt or JavaScript in the native app. Preserve raw Markdown as the authoritative content and derive visual attributes. This is a recommendation based on the current source, not an Apple requirement.

## Explicit saving, recovery, and NSDocument

**API facts:** `autosavesInPlace` defaults to false. Opting in changes where autosave writes and influences close/termination alerts. `scheduleAutosaving()` exists for crash protection; autosave operations can target an autosave directory instead of the source file. `autosavesDrafts` is a separate capability, defaulting to true, whose save operation can change the draft's current location. These are distinct from explicit Save. [autosavesInPlace](https://developer.apple.com/documentation/appkit/nsdocument/autosavesinplace), [scheduleAutosaving](https://developer.apple.com/documentation/appkit/nsdocument/scheduleautosaving()), [autosavesDrafts](https://developer.apple.com/documentation/appkit/nsdocument/autosavesdrafts)

**Recommendation:** Preserve the current editor's explicit Save contract by default. Never choose in-place autosave merely to obtain native APIs: it would write named files before the user presses Command-S. Prefer NSDocument autosave-elsewhere recovery if a lifecycle spike proves it preserves the source and restores both named and untitled documents. Set/document draft behavior deliberately. Test close, Quit, cancelled Save As, failed writes, multiple windows, forced termination, and recovery after the source was changed or deleted. Recovery must not overwrite the changed source automatically.

The current Qt backend uses separate recovery JSON, a 750 ms timer, and `QSaveFile` for source/recovery writes. If AppKit recovery cannot meet that behavior, use a dedicated recovery store with stable document IDs and source baseline metadata. Do not run two overlapping recovery systems. AppKit offers an autosave URL and reopening support; custom recovery formats require additional reopening work. [autosavedContentsFileURL](https://developer.apple.com/documentation/appkit/nsdocument/autosavedcontentsfileurl), [autosavingFileType](https://developer.apple.com/documentation/appkit/nsdocument/autosavingfiletype)

## File coordination and external changes

**API facts:** NSDocument implements file presentation and coordination, but Apple's archived document guide explicitly instructs enabling `autosavesInPlace` to enable its file coordination. Current `NSFilePresenter` documentation says direct low-level writes do **not** notify presenters. Coordination therefore cannot be treated as a universal filesystem lock or detector. [Document lifecycle guide](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocBasedAppProgrammingGuideForOSX/ManagingLifecycle/ManagingLifecycle.html), [NSFilePresenter](https://developer.apple.com/documentation/foundation/nsfilepresenter)

**Recommendation:** Make explicit-save NSDocument coordination a mandatory early spike. Establish which NSDocument hooks operate with in-place autosave disabled; add a single coordinated DocumentIO boundary if necessary. Avoid a second presenter registered for the same document without a demonstrated need. Pair coordination with supplemental file/directory observation, reattachment after atomic replacement, and content-baseline comparison immediately before explicit Save. React to move, deletion, permission loss, and changed bytes. Preserve local work and offer Reload, Keep Local/Save Copy, or an explicit overwrite decision; a clean buffer may reload only under the documented product policy.

Never resolve a detected conflict by silently updating the baseline and writing over the external version. Save a local recovery snapshot and retain the external version before an authorized overwrite. There is still an unavoidable race against writers that do not participate in coordination; describe this practical limit and test ordinary shell writes and atomic replacement, not only coordinated test writers. NSDocument's Versions conflict UI addresses document-version conflicts and should not be assumed to handle every local-editor conflict.

Custom coordinators should be short-lived, use a suitable operation queue, and identify the initiating presenter to avoid self-notifications/deadlocks. Do not synchronously block the main thread waiting for callbacks that need that same thread. [NSFileCoordinator](https://developer.apple.com/documentation/foundation/nsfilecoordinator), [init(filePresenter:)](https://developer.apple.com/documentation/foundation/nsfilecoordinator/init(filepresenter:))

## TextKit choice and hidden Markdown syntax

**API facts:** NSTextView supports modern TextKit 2 and legacy TextKit 1. Apple recommends TextKit 2 for performance and international text. Accessing `layoutManager` can cause a one-way compatibility transition to TextKit 1; a text view cannot run both layout managers simultaneously. TextKit 2 has rendering attributes, while TextKit 1 offers glyph generation customization and a `.null` glyph property that the layout manager ignores. [TextKit](https://developer.apple.com/documentation/appkit/textkit), [WWDC22 text views](https://developer.apple.com/videos/play/wwdc2022/10090/), [rendering attributes](https://developer.apple.com/documentation/appkit/nstextlayoutmanager/setrenderingattributes(_:for:)), [NSLayoutManagerDelegate](https://developer.apple.com/documentation/appkit/nslayoutmanagerdelegate), [null glyph](https://developer.apple.com/documentation/appkit/nslayoutmanager/glyphproperty/null)

**Recommendation:** Time-box two source-preserving prototypes before selecting the engine. Prototype TextKit 2 styled Markdown first; rendering attributes alone are not evidence of zero-width hidden syntax. Compare an explicitly constructed TextKit 1 stack using glyph delegation for concealed delimiters/link destinations. Neither candidate passes until pointer placement, arrow/word movement, selection across hidden spans, deletion, copy/paste, undo/redo, search/replace, wrapping, accessibility, printing, and IME work. Do not copy the Qt tiny-font/negative-spacing trick or remove syntax from the backing string. Any hidden glyph approach remains an engineering hypothesis until these behaviors pass.

If TextKit 2 cannot satisfy the hidden-syntax contract, select TextKit 1 explicitly and record why. Never trigger fallback accidentally by inspecting a legacy property. If neither candidate passes, revise the plan to a visible/dim-syntax editing mode with a clearly recorded parity deviation before production work.

Use UTF-16 ranges at AppKit/module boundaries: NSString indexes count UTF-16 units, whereas Swift `String` indexes are not integer character offsets. Convert with `Range(nsRange, in: text)` and `NSRange(swiftRange, in: text)` and reject invalid ranges. Cover emoji, combining marks, surrogate pairs, RTL, and mixed scripts. [Characters and grapheme clusters](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Strings/Articles/stringsClusters.html), [String.UTF16View](https://developer.apple.com/documentation/swift/string/utf16view)

Apply programmatic source edits through NSTextView's change protocol (`shouldChangeText`, an undoable replacement, then `didChangeText`), not repeated whole-buffer assignment. Route view undo to the document's undo manager. Render-only highlighting must not create undo operations or mark the document dirty. Defer mutation shortcuts and disruptive syntax hiding while `hasMarkedText()` is true; let NSTextView own composition. [didChangeText](https://developer.apple.com/documentation/appkit/nstextview/didchangetext()), [NSTextViewDelegate](https://developer.apple.com/documentation/appkit/nstextviewdelegate), [NSTextInputClient](https://developer.apple.com/documentation/appkit/nstextinputclient)

## Native find, printing, and windows

NSTextView can use the native find bar via `usesFindBar`, with incremental search support. Prefer its standard actions and Command-F/Command-G rather than cloning the QML search UI. Verify Replace All is one undoable edit and searches raw Markdown including concealed syntax. [usesFindBar](https://developer.apple.com/documentation/appkit/nstextview/usesfindbar)

NSDocument supplies `printInfo` and a print-operation override. Provide a separate print view/snapshot with explicit light-paper typography, pagination, and a stated source-versus-styled-output policy; do not print the live scrolled viewport. Test the native print sheet and Save as PDF. NSDocument's window-controller APIs support the window lifecycle; use standard New/Open/recent-document/menu actions and retain the app after the last document window closes. These are project recommendations around available APIs. [printInfo](https://developer.apple.com/documentation/appkit/nsdocument/printinfo), [NSDocument](https://developer.apple.com/documentation/appkit/nsdocument/)

## Sandbox and distribution

**API facts:** The Mac App Store requires App Sandbox. Direct notarized distribution requires hardened runtime, while sandboxing is optional. Open/save panels grant access to selected documents; persistent access can use security-scoped bookmarks. Resolving a stored bookmark does not automatically activate access. Successful `startAccessingSecurityScopedResource()` calls must be balanced with `stopAccessingSecurityScopedResource()` to avoid leaking system resources. Ordinary permissions can still deny I/O. [Distribution preparation](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), [Security-scoped access](https://developer.apple.com/documentation/foundation/nsurl/startaccessingsecurityscopedresource())

**Recommendation:** Start sandboxed with user-selected read/write access and app-scoped bookmarks only where custom persistent access needs them. Use a small FileAccess service for bookmark refresh/reselection, shared access lifetimes, permission errors, and cleanup. Store recovery in the app container. Test open, save, relaunch, rename, stale bookmark, revoked permissions, and external-change monitoring in the sandbox. Do not request broad filesystem or network privileges for this offline editor.

Recommend a Developer ID signed, notarized, stapled `.app`/DMG for the first release. Distribution needs an actual team, bundle identifier, signing certificate, and notarization credentials; unsigned local builds remain a separate reproducible path. Use `notarytool`, not retired `altool`; include hardened runtime and secure timestamps, exclude debug `get-task-allow`, check notarization logs, validate stapling/signatures/Gatekeeper, then test the downloaded quarantined artifact. Account provisioning is a human prerequisite, not work an implementation agent can manufacture. [Notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Command-line notarization](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
